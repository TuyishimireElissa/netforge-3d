# Security model and range gating
Trust boundaries: user keyboard -> Godot -> local JSON bridge -> bounded action dispatcher -> own simulation; **no direct subprocess, shell, host scan or packet capture**. Bridge has random per-process token, custom HTTP header, constant-time comparison, max request body, length-bounded CLI, no permissive CORS, single address bound to loopback and locked model. HTTP transport is plaintext loopback; same-host malware can attack local process/token. This is *not* a hardened multi-user/authenticated remote service. No secrets persisted. Avoid running bridge on shared untrusted machines.

Threats: local malicious origin/process, forged requests, excess payload, malformed JSON, output disclosure, configuration spoofing, terminal privilege confusion, drift between visual and logical state. Controls: token on every action and state read, whitelisted operations and device IDs, tests for invalid targets, no host shell, state snapshots returned from backend. Residual: HTTP server has no rate limit/concurrent client binding, token entered in UI memory, no TLS, no resource quota on clients, logs not redact-aware, and no tamper-resistant audit. SQLite v1 stores topology, commands as bounded event text and simulated traces in the local user's home; access control comes from OS file permissions, not encryption. No session token is stored. Checkpoint IDs are type-checked and bounded to 20; invalid future schema versions fail closed. A compromised local account can alter the DB; do not expose the port or store sensitive real-lab evidence there.

**Mandatory gate before *any* real cyber range:** explicit per-session authorized target inventory; disposable topology/images; VM-grade separation for high risk; deny Internet egress and host/private-network routes by default; narrowly delegated privileges; cgroup/VM CPU/RAM/process/disk/time quotas; argv-only allowlisted tools; timeout/cancel and output caps; immutable operation audit without secrets; verifiable stop/reset/snapshot; failed-cleanup alarm; isolation tests from inside guest and host; explicit opt-in for any exceptional egress. A container alone is not sufficient for high-risk malware/vulnerable exercises. The current simulator is not a security boundary for real attacks and **must not** be used to run testing tools.

Verification uses a fixed test-only token in a local fixture, a temporary SQLite file, and an ephemeral loopback port. The GDScript override accepts only literal `http://127.0.0.1:<valid-port>`; it cannot send the session token to a remote origin through this setting. CI permissions are `contents: read`; no credentials or network appliance images are downloaded. Engine archive SHA512 is checked against the corresponding official release checksum before use. This CI smoke is not evidence of real laboratory isolation.

Hosted CI run 38756303805 is evidence only for simulated loopback lab flows; it does **not** establish containment, authorized target enforcement, quotas or safe execution of real tools.
