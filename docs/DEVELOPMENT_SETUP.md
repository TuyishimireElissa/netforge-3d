# Development setup (Windows 10 8 GB / Linux)
Use Python 3.11+ and Godot 4.2+ desktop editor, downloaded from official sources ([Godot documentation](https://docs.godotengine.org/en/stable/), [official Godot downloads](https://godotengine.org/download/), [Python documentation](https://docs.python.org/3/)); no Python pip packages needed. These official-site links are setup references; direct external-site access was unavailable in this sandbox, so only the GitHub Godot license source was machine-checked here. Do not install Docker or virtualization for this slice. From repository root:

```powershell
py -3 -m unittest discover -s tests -v
py -3 -m tools.console
py -3 -m backend.server            # default local SQLite at ~/.netforge-3d/labs.sqlite3
```

On Linux substitute `python3`. Bridge prints a new secret token; keep terminal open. Open Godot project manager, **Import** `game/project.godot`, edit/run scene (F6) or run project (F5), paste token, click Connect. On Windows, firewall should not require an inbound rule: bridge binds `127.0.0.1` only. Godot and Python bridge must run on the **same computer**; hardcoded port 8765 must be free. `NETFORGE_NAME` changes backend product name (`set NETFORGE_NAME=...` in cmd, `$env:NETFORGE_NAME=...` in PowerShell); Godot window title remains static. If Godot cannot connect, verify server remains running, token matches and port is available. If Godot parser errors, capture the exact editor output: the Godot 3D flow was not runtime-verified here (no Godot installed). Do not use the bridge on a public host or change its bind address.

Repro mission: connect PC B cable, run ping B→A; for B use `enable`, `configure terminal`, `interface fastethernet 0/3`, `switchport port-security`, `switchport port-security mac-address sticky`, `end`, run ping B→A, `show port-security`, `write memory`, Assess. If CLI field lacks focus, press Escape to release pointer. `python -m tools.console` provides identical model without Godot. Default bridge changes persist across process restart. **Reset** restores the disconnected initial topology but keeps saved checkpoints; **Restore latest checkpoint** reverts to the last saved snapshot. Use `--ephemeral` for no database (checkpoint controls report unsupported), or `--db PATH` for a separate persistent file. `tools.console` is always ephemeral. Do not copy the database to a shared computer without reviewing its contents. Full real networking/range requires future architecture and safety work, not extra setup flags.

## Automated verification (added 2026-10-15)

From repository root, `py -3 -m tools.verify --download-godot` on Windows (or `python3 -m tools.verify --download-godot` on Linux) runs Python tests, syntax, JSON/schema and static project checks, then attempts the **official pinned Godot 4.2.2** release. It writes per-stage logs and a structured `artifacts/verification/report.json` (ignored by Git). Add `--require-godot` to make unavailable/skipped engine checks exit nonzero; CI always does this. Alternatively use `--godot PATH_TO_4.2.2_EXECUTABLE --require-godot`. The verifier never uses a remote backend: for headless Godot integration it starts its own ephemeral-port loopback SQLite fixture with a test token. The Godot client accepts `NETFORGE_API_URL` only for `http://127.0.0.1:<port>` and otherwise keeps its default `127.0.0.1:8765`.

The Windows Actions workflow installs the Python package from `pyproject.toml`, downloads the official 4.2.2 win64 ZIP, validates it against the release's SHA512-SUMS.txt, imports `game/`, launches its main scene headlessly and runs `game/tests/smoke.gd` against a real local HTTP fixture. A headless check tests scripts and model synchronization, **not** full graphical rendering or human usability. The Python wheel contains Python modules and scenario JSON, not the Godot game directory; a full distributable remains future work.
