# Master specification — 2026-10-15

## Product and invariants
NetForge 3D is a configurable-name, offline-first training platform connecting a 3D inventory, authoritative equipment/topology state, traceable simulations and optional isolated real labs. Product name is currently set by `NETFORGE_NAME` on the backend; Godot project title is still static. Audience: students, instructors and authorized security trainees; first target: Windows 10, 8 GB RAM; no FPS or max-size promises without measurement.

**Truth rule:** each capability MUST be labeled SIMULATED, REAL TOOL OR SERVICE, EMULATED DEVICE, VISUAL ONLY, or PLANNED/BLOCKED/UNSUPPORTED. Never call model traces a capture, a CLI an actual vendor NOS or an unisolated process a safe range. The support registers below are authoritative for today's release. The built-in provider never runs host commands. No unauthorized targets.

## Functional contracts
1. A unique equipment ID and interface ID identify every functional world object; all cable/port visuals mirror backend state. Connection requires medium and free compatible ports. Commands, packets, mission evidence and reset all operate on the same state.
2. Core topology and events are renderer-independent. Each success/failure is explained by traceable modeled decisions. Configuration modes reject unsupported commands; errors do not mutate state. Saves must declare durability and version.
3. Scenario definitions specify objectives, initial state, tools, authorized targets, scoring criteria, evidence, failure/reset and hints. Outcome-based checks must not rely solely on typed commands. Avoid unsafe tool access.
4. Real providers must advertise each supported operation, diagnose missing runtime, isolate lab traffic and resources, deny egress/host access by default, log execution and perform verified cleanup. The simulator does **not** satisfy these real-range controls.
5. Deployment: local single-player first, then SQLite v1 single-lab persistence and simulated checkpoints (now tested), later authenticated multi-user services and remote lab control with TLS and authorization. Never promote the local token bridge unchanged to remote service.
6. UX: first-person selection; accessible status, objective/hint, CLI and packet trace; settings for mouse sensitivity, graphics, audio, readable typography, remapping, save/reset; avoid fabricated success feedback. Current controls are minimal; checkpoint buttons are authored but still require Godot runtime smoke.
