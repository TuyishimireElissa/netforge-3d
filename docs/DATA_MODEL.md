# Data model and persistence (schema v1)

**Current implemented state (SIMULATED):** `Lab` has `Port`, `Link`, MAC table, synthetic trace/events, CLI mode and saved switch configuration. The bridge defaults to `~/.netforge-3d/labs.sqlite3`; `--db PATH` chooses another path; `--ephemeral` disables SQLite. `tools.console` remains ephemeral. A bridge restart restores its last successful action, including the *modeled* trace/mission evidence. Reset restores initial lab topology and clears active configuration while retaining user-created checkpoints. `write memory` is durable **only when called through the SQLite-backed bridge**; headless console stays in-process. The bridge does not store a token or other credentials in SQLite.

SQLite v1 tables (`database/store.py`): `revisions` (one active and up to 20 explicit checkpoints; CLI mode and last ping), `port_states` (device/interface/configuration), `links` (physical connectivity), `learned_macs` (per-port), `mac_entries` (VLAN forwarding), `saved_ports` and `saved_sticky_macs` (saved CLI configuration), `messages` (bounded synthetic trace and audit events). Foreign keys and uniqueness constrain relationships. Active writes delete and replace one revision atomically; checkpoint revisions have stable IDs. The app serializes requests, migration 0→1 executes in a transaction, `PRAGMA user_version` rejects unknown future versions, `quick_check` runs on open, and a failed save rolls back. No everything-in-one-JSON-column design. No downgrade or repair of corrupted files is implemented; back up before upgrading. SQLite is a local store, **not** a network-range isolation control.

`scenarios/mission_*.json` are now validated `schema_version=1` definitions loaded on program import. Fields: `id`, `api_key`, `name`, `difficulty`, `fidelity`, `prerequisites`, `objectives`, `initial_topology`, `starting_problem`, `available_equipment`, `authorized_targets`, `tasks`, `hints`, `rubric`, `required_evidence`, `success`, `failure`, `recovery`, `report`. Rubric weights 1–10 refer only to registered state/evidence criteria; success may AND each listed criterion exactly once. No Python eval or executable command is accepted. Mission A/B results use names `mission_a`/`mission_b` for existing clients and include criterion booleans, score/max_score and prerequisites. Narrative tasks, failure and report fields are informational; a printable professional completion report, progress profile and authored mission editor are not implemented. New criteria require code and tests, not merely JSON edits.

**Future normalized data (not implemented):** equipment templates, topology/profile/owner, IP pools, routes, services, firewall rules, users, centralized logs/evidence hashes, tool inventory and capability/fidelity register tables, protocol state as needed. Future migrations must use versioned transactional upgrades and old-file fixture tests. PostgreSQL only when multi-user central administration requires it. No tool or VM state is captured by these simulated checkpoints.

The browser companion is a separate `App` instance without a `SQLiteStore`: changes and simulated `write memory` are shared by connected viewers in **that process only**. No checkpoint/restore/delete actions are exposed there. The packaged wheel includes its HTML/CSS/JS files but still excludes the desktop Godot project; installing the wheel does not create a packaged game.
